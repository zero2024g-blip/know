A correction to what I told you last time

Last turn I said the unescaped created_by in Admin/referral.php was an exploitable stored XSS that could hand over an admin session. That was wrong.

Not exploitable

The unescaped output cannot carry a payload

app/Controllers/Auth.php:164 · app/Controllers/User.php:198

Every value reaching those unescaped <?= tags is constrained at its entry point. username is alpha_numeric at registration, at login and at admin edit — so <, > and quotes can never be stored. fullname is alpha_space and passed through esc() before insert. id_reff is an auto-increment integer, code is random_string('alnum', 6), set_saldo is numeric.

I should have checked the validation rules before calling it exploitable. The unescaped output is still worth fixing as defence-in-depth — it is one loosened rule away from being real — but it is a hygiene item, not the emergency I described.

Critical

Both are secrets in source. Neither depends on an attacker finding a clever bug.

Critical

The encryption key is a short dictionary word

.env → encryption.key

Eight lowercase letters, and a phrase a wordlist would carry. CodeIgniter's Encryption service derives from this key — anything you encrypt or sign with it is forgeable by anyone who guesses it, and any attacker who ever obtains a ciphertext can brute-force this in seconds.

It matters more the moment you build the share-link tokens we designed: those tokens are exactly the kind of thing that would be signed with this key.

Fix
php spark key:generate     # writes a 32-byte random key

encryption.key = g████████
encryption.key = hex2bin:9f2c...   # 64 hex chars
Critical

A hardcoded password, sent in the URL

app/Controllers/Keys.php:88–100 — api_key_reset()

$pass = $this->request->getGet('pass'); … if ($pass == 't██████' …)

Three problems stacked. The secret is seven characters, committed in source. It travels as a GET parameter, which means it is written into Apache access logs, Cloudflare's request logs, browser history, and any Referer header sent to a third party. And the comparison is == rather than a constant-time check.

The route sits behind the auth filter, so this is not an unauthenticated hole — but a shared static secret in a query string is the kind of thing that leaks quietly and is never rotated.

Fix
$pass = $this->request->getGet('pass');
if ($pass == 't██████' and $db_key) {
$pass = (string) $this->request->getPost('pass');   // POST, never GET
if (hash_equals(getenv('api.resetSecret'), $pass) && $db_key) {

High

High

The rate limiter trusts a header anyone can set

app/Controllers/Auth.php — clientIp()

CF-Connecting-IP is read and used directly, with no check that the request actually arrived from Cloudflare. Login throttling keys off that value, so a forged header means every attempt looks like a new IP and the limiter never fires — unlimited password guessing against Argon2id.

Today your .htaccess saves you: Require ip restricts the origin to Cloudflare's ranges, and Cloudflare overwrites the header. So this is not currently exploitable — but it means one config change is all that stands between you and unmetered brute force. That is too thin for the control that protects every account.

Fix — verify the peer before trusting the header
private function clientIp(): string
{
    $remote = $this->request->getIPAddress();
    if (! $this->fromCloudflare($remote)) {
        return $remote;              // header is not trustworthy here
    }
    $cf = $this->request->getServer('HTTP_CF_CONNECTING_IP');
    return filter_var($cf, FILTER_VALIDATE_IP) ?: $remote;
}

Keep the Cloudflare range list in one place and refresh it — they publish it at cloudflare.com/ips and it does change. The list in your .htaccess is a point-in-time copy.

High

AdminFilter allows the request when its checks don't run

app/Filters/AdminFilter.php

The filter only denies inside a nested if. Fall outside it and the method returns null, which CodeIgniter reads as allow:

if ($session->userid and $session->time_login) {
    $user = $userModel->getUser($session->userid);
    if ($user) {
        if ($user->level != 1) { return redirect()… }   // only exit that denies
    }
}
// no session      → falls through → ALLOWED
// user row gone   → $user falsy → ALLOWED

The unauthenticated path is covered by AuthFilter running first, so that half is not reachable. The second half is: delete a user row while their session is live and that session gains admin access to every /admin/* route. Narrow, but real — and the shape is wrong regardless. An authorisation filter should deny by default and allow only on proof.

Fix — invert it
$user = $session->userid ? (new UserModel)->getUser($session->userid) : null;
if (! $user || (int) $user->level !== 1) {
    return redirect()->to('dashboard')->with('msgWarning', 'Access Denied!');
}
return;   // only an actual admin reaches here
High

Key-existence oracle before the password check

app/Controllers/Keys.php — api_key_reset()

$db_key = $model->getKeys($keys); runs before the secret is validated, and the response always includes 'registered' => $db_key ? true : false — regardless of whether pass was correct.

So any signed-in account can probe arbitrary key strings and learn which ones exist, without owning them and without the secret. The sleep(1) slows a single thread; it does nothing against parallel requests. For a panel whose whole product is the keys, a validity oracle is the wrong thing to hand out.

Fix

Validate the secret first and return an identical response for both "wrong secret" and "no such key". Scope the lookup to the caller unless they are admin, and rate-limit the endpoint per account, not just per IP.

Medium

Medium

Blurring the key is CSS, not protection

app/Models/KeysModel.php — API_getKeys() · Views/Keys/list.php:81

The DataTables endpoint selects user_key and returns it in plaintext JSON. The "Hide keys" toggle adds a CSS class that applies filter: blur(3px). The network tab, or a direct call to keys/api, returns every key unobscured.

The scoping itself is correct — API_getKeys() filters by registrator for non-admins, so this is not a cross-user leak. The issue is the false assurance: the toggle looks like a security control and isn't one. And for an admin session it is the single request that dumps every key in the system, which makes it the obvious target if a session is ever stolen.

Fix

Return a masked value by default (ZM-8QK4-****-****) and serve the full key from a separate, per-row, rate-limited endpoint that logs each reveal to the activity log. Then "Hide keys" is describing something true.

Medium

CSP is fully written, then switched off

.env → app.CSPEnabled = false · .htaccess section 1

You configured every CSP directive in .env — defaultSrc 'none', scriptSrc 'self', the lot — and then left CSPEnabled = false, so none of it is sent. The header that is sent comes from .htaccess and contains script-src … 'unsafe-inline', which permits exactly the injection a CSP exists to stop.

You can't simply flip it on: the panel uses inline <script> blocks throughout the views, and 'self' would break them. Doing this properly means nonces.

Fix — in order

Move inline scripts to files under public/assets/js, or emit a per-request nonce and add it to each block. Then set CSPEnabled = true and drop 'unsafe-inline' from the .htaccess header so the two stop contradicting each other. Run with reportOnly = true first to see what breaks.

Medium

The old password scheme still exists on dormant accounts

app/Helpers/nata_helper.php:10

md5("X███████████████" . $password) then bcrypt at cost 8. The pepper is in source, MD5 is fast, and cost 8 is well below a sane 2026 setting.

Your migration is done properly — login verifies against the legacy hash, then password_needs_rehash upgrades to Argon2id. But it only fires when someone logs in. Accounts that have been idle since the change still carry the weak hash indefinitely.

Fix

Query how many rows still hold a bcrypt-$2y$08$ hash. Force a reset on those accounts, then delete create_password() and the fallback branch entirely so the weak path cannot come back.

Medium

Sessions last 30 days

.env → app.sessionExpiration = 2592000 · cookie.expires = 2592000

A month-long session on a panel that holds balance and can revoke every key. The in-app timer is much tighter — 24 hours with "keep me signed in", 30 minutes without — so the framework value mostly governs how long a stolen cookie stays useful.

Bring it down to something like 7 days, and build the Active sessions screen we designed so you can actually revoke one.

Low — worth cleaning up

Low

The LFI guard in index.php does nothing

index.php:7
define('FCPATH', __DIR__ . DIRECTORY_SEPARATOR);

// 🔴 جلوگیری از حملات LFI
if (strpos($filename, '..') !== false || strpos($filename, '/') !== false) {
    die("Access Denied!");
}

$filename is never assigned — not in this file, not anywhere. It is always null, strpos(null, '..') is always false, and the branch never runs. On PHP 8.1+ it also emits a deprecation notice on every single request.

It reads like protection and provides none, which is worse than having nothing there — someone reviewing this file later will assume LFI is handled. Delete it. Path traversal is not the front controller's job anyway.

Low

The API exception in .htaccess skips every rule after it

.htaccess section 3A

RewriteRule ^.*zezr_connector.*$ - [L,NC] sits first and carries [L]. Any URL containing that string therefore bypasses rules B through F — the direct-IP block, the HTTPS redirect, the method filter and the query-string injection filter.

It also matches on substring, so /anything/zezr_connector/anything qualifies. Anchor it to the real route and let the rest of the chain apply, or move it below the filters it doesn't need to skip.

Low

A stale backup sits in the webroot

public/default.php.old.php

It ends in .php, so it executes rather than downloading. Old copies of live files are a standard place for an outdated code path to survive a fix. Remove it — the .bak pattern in your FilesMatch block does not catch this name.

Low

Escaping happens on write instead of on output

app/Controllers/User.php:216, 318

'fullname' => esc($fullname) stores HTML entities in the database. A name with an apostrophe comes back as &#39; forever, and if you later add esc() on output — which you should — it double-escapes. Store the raw value; escape when rendering.

Performance — where the lag actually is

The panel is not slow because of PHP. It is slow because of what the browser has to fetch before it can paint, and one query that reads far more than it needs.

Medium

Every key in the table is loaded to answer a yes/no question

app/Controllers/Keys.php — index()

$keys = $model->findAll(); pulls every row with every column into PHP memory. The view then uses it for exactly one thing:

Views/Keys/list.php:21    <?php if ($keylist) : ?>

That is the only reference. The table itself is populated by the server-side DataTables endpoint, so the entire result set is fetched, hydrated into objects, and thrown away on every page load. At 1,284 keys that is already wasteful; it grows linearly and will eventually hit the memory limit.

User::manage_users() does the same via getUserList().

Fix
$keys = $model->findAll();
'keylist' => $keys,
'has_keys' => $model->where($scope)->countAllResults(),
Medium

Four external hosts before the page can render

app/Views/Layout/Starter.php

cdn.jsdelivr.net, code.jquery.com, cdnjs.cloudflare.com, fonts.googleapis.com — four DNS lookups and four TLS handshakes, each a full round trip, before the first paint. On a phone on mobile data that is most of the perceived load time. Your own assets total 16 KB.

There is a correctness angle too: you are pinned to bootstrap@5.0.2, which is years of fixes behind, and every one of those hosts can see your users' IPs on every page view.

Fix

Download all four into public/assets and serve them from your own origin. Cloudflare caches them at the edge for free, so you get one connection reused for everything instead of four cold ones. Self-host the Poppins and JetBrains Mono files too, with font-display: swap and a preload for the weights you actually use.

Low

Cloudflare free — three settings worth checking

deployment

Never cache an authenticated page. Send Cache-Control: private, no-store on everything behind the auth filter, and on the share-link claim page when you build it. A signed-in page cached at the edge and served to someone else is the worst kind of leak, and it is a configuration mistake rather than a code one.

Keep the origin allowlist current. Cloudflare adds ranges; the copy in your .htaccess is frozen at the day it was written. When a new range appears, real users get 403s and you will be debugging the wrong thing.

Turn on Bot Fight Mode and put a rate-limiting rule on /login and /check. The free plan allows one rule — spend it on /check, since that is your only unauthenticated endpoint that answers questions about keys.
